# payable-edge-gateway

A Cloudflare Worker that lets a website charge AI agents per request, and charges them only for what it delivered.

It checks who the agent is (Web Bot Auth, RFC 9421 signatures with Ed25519), quotes a price per caller and route,
takes an x402 payment, and settles that payment only after the origin has answered successfully, or, for
outcome-priced routes, only when the origin says the outcome happened. One Durable Object per paying wallet makes
sure a signed payment pays for one request, once, even when twenty copies of it arrive at the same moment. Money is
integers end to end, and the seller's book is reconciled against the chain on every report.

Cloudflare's [Monetization Gateway](https://blog.cloudflare.com/monetization-gateway/) (announced July 2026) gives
"$0.99 per resolved support escalation", "paid only when the work succeeds", as an example price, without saying
how the success is checked. This repository is one worked answer to that question, small enough to read in an
afternoon, with the hard cases tested inside workerd.

## How a paid request goes

```
agent ──signed request──▶ verify Web Bot Auth ──invalid──▶ 401
                              │
                              ▼
                        price for (route, caller) ──block──▶ 403      free ──▶ origin
                              │
                    no X-PAYMENT ──▶ 402 with the price (x402 "accepts")
                              │
                    decode, match amount / recipient / network, key belongs to the payer
                              │
                    PayerLedger.reserve(nonce)          one Durable Object per wallet: single writer
                       ├─ already settled, same page, within 5 min ──▶ deliver again, no charge
                       ├─ already settled, other page ──▶ 402 "payment already used"
                       ├─ in flight elsewhere ──▶ 402 "payment in use by another request"
                       └─ over the wallet's daily cap ──▶ 402 "payer spending limit reached"
                              │
                    facilitator.verify ──invalid──▶ release, 402
                              │
                    origin ──not 2xx, or outcome not met──▶ release, pass the answer on, no charge
                              │
                    facilitator.settle ──failed──▶ release, 402 (the content is not sent)
                              │
                    PayerLedger.commit, SellerBook.recordSale (exactly once per transaction)
                              ▼
                    200 + X-PAYMENT-RESPONSE
```

Why this order:

- **Reserve before verify.** The per-payer Durable Object is the only place two copies of one payment can meet, so
  it decides first; the facilitator never sees the losing copies.
- **Settle after delivery.** Settling first and refunding later means refunds, disputes and a window where the agent
  has paid for nothing. Settling after the origin answers, and before the content leaves, means the seller is never
  paid for a failure and never gives away content unpaid.
- **The chain is the backstop.** If a Worker dies between settling and committing, the reservation goes stale and
  can be taken over, and the chain refuses the already-used nonce, so the takeover cannot charge twice.
- **Outcomes are a contract with the origin.** An outcome-priced rule names a response header and value
  (`x-outcome: resolved`); anything else is served and not charged, and the same authorization can pay later.

## What it covers

| | |
|---|---|
| `src/webbotauth.ts` | RFC 9421 signature base, Signature-Input parsing, RFC 7638 JWK thumbprints, key directory lookup, created/expires window, signing for agents |
| `src/x402.ts` | x402 v1 `402` body, `X-PAYMENT` / `X-PAYMENT-RESPONSE`, the `exact` scheme's authorization, an HTTP facilitator client |
| `src/pricing.ts` + `config/pricing.json` | rules by route and caller (verified, unverified, partner), free / block / charge, on delivery or on outcome |
| `src/ledger.ts` | `PayerLedger`: reserved, settled, released; lease takeover; redelivery window; a rolling per-wallet spending cap |
| `src/seller.ts` | `SellerBook`: sales keyed by transaction, so a sale is recorded once; revenue by operator and rule; refusal counters |
| `src/money.ts` | atomic amounts as `bigint`, parsed from integer strings only |
| `src/sim.ts` | a simulated facilitator and chain (Durable Objects) so everything runs offline |
| `web/` | the seller's console: who paid, for what, what was served free, what was refused, and whether the book agrees with the chain |

## Run it

```bash
npm ci
npm test               # tests inside workerd (vitest + @cloudflare/vitest-pool-workers)
npm run typecheck
npm run sim            # starts the Worker in workerd, drives 4,000 agent tasks, writes reports/sim.json
npm run test:report && npm run report    # refreshes the dashboard above
npx wrangler dev       # the gateway on :8787
cd web && npm ci && npm run dev          # the console; reads the last simulation, or the live gateway with the admin token
```

The simulator signs and pays exactly as an agent would, using the same client helpers an agent would import
(`signRequest`, `encodePayment`), not the gateway's internals. It works out on its own what every request should
have cost, then checks all 80 wallet balances, the seller book and the chain against that.

## What is simulated, and other limits

- **The money is not real.** The facilitator and chain are Durable Objects. Payment authorizations carry the same
  fields as x402's `exact` scheme on EVM (EIP-3009 `from`, `to`, `value`, `validAfter`, `validBefore`, `nonce`), but
  are signed with Ed25519 rather than EIP-712 secp256k1, and the payer's address is derived from that key. Pointing
  `FACILITATOR_URL` at a real x402 facilitator swaps in the HTTP client; that path is written, not exercised here.
- **Latency is from one machine.** Worker, Durable Objects and the simulator share one local workerd process and CPU.
  The unloaded figures say what the payment path adds; they are not edge numbers.
- **The seller book is written after the response** (`waitUntil`). A lost write would show up as a reconciliation
  difference in the report; there is no repair job.
- **Only the `exact` scheme.** Cloudflare's proposed deferred scheme (sign now, settle in a daily batch) is not built.
- **Key directories** for `*.agents.sim` come from a registry Durable Object; other hosts are fetched and cached.
- Not deployed to a Cloudflare account.

## Layout

```
src/            the Worker: gateway, Web Bot Auth, x402, pricing, ledger, seller book, simulated chain
config/         pricing.json: seller, limits, rules (every setting lives here)
test/           workerd tests: protocol vectors, pricing, payment, replay, concurrency, outcomes, cap, admin
scripts/        simulate.ts (load and attack run), report.ts (writes the dashboard)
reports/        generated: sim.json, tests.json, web-tests.json
web/            seller console (React, Framer Motion), feature-first: features/sales, shared/{theme,ui,format}
```
